# 覆盖层性能优化

## Goal

降低 SLUI 覆盖层（overlay 窗口）在游戏运行期间的主线程、渲染和资源开销，让覆盖层长时间叠在游戏上方时占用更少 CPU/GPU，
同时不改变任何可见行为、协议和输入模式。

## Background

> 2026-10-31 重新规划。首版规划（提交 `5a1cced`）分析的是过时快照（`23q3/slui` main，最后提交 2026-10-03）。
> 之后合入的 #33（v6 插件房间布局）、#53（时钟移出 `App`、面板 memo）、#54（WOFF2 字体）、#55（正式包不含 mock）
> 以及 10-21 的 backdrop 系列任务，已经交付了首版子任务 1、3 的全部内容和 4、5、6 的大部分内容。
> 下列结论来自在 `fb3f5ce`（0.11.0）上的重测，数据、复现命令和未测项见 `research/perf-baseline.md`。

- 只有雷达子树按显示刷新率重渲染：雷达时钟跑在 `requestAnimationFrame` 上（无头 60 Hz 下约 75 次/秒，含 15 Hz 位置帧），`App` 约 1 次/秒，HUD/商店/聊天等面板 0 次/秒。
  地图层每帧只改写一个相机变换。在 144 Hz 显示器上雷达约 159 次/秒，以下每次渲染的开销都按约 2.1 倍放大。
- 小地图模型：默认配置每次渲染约 20 µs（约 1.5 ms/s）；「非居中」相机每次调用 18–26 µs，「全图」相机 24–30 µs；
  最坏配置（动态缩放 + 朝向向上 + 非居中）每次渲染约 250–270 µs，即 75 次/秒时约 20 ms CPU/s（144 Hz 约 41 ms/s）。
  （首版重测用 `vm` 沙箱运行，数字被放大约 5 倍，已更正，见 `research/perf-baseline.md`。）
  原因与首版分析一致（`camera.ts:49-67` 每次重建全部角点并展开求最值，`dynamicZoom.ts:14-33` 最多 22 次相机计算，reducer 与 selector 各算一遍），只是代码位置和地图数据变了。
- 正式包已不含 mock（`App-*.js` 199 KB）。资源体积：字体 13 MB（已是 WOFF2），商店物品 PNG 4.3 MB（无损 WebP 约 2.85 MB，q90 约 0.87 MB）。
- 其他测到的开销：`backdrop.ts` 的 rAF 测量循环每帧对每个登记面板沿祖先链调用 `getComputedStyle`，开发版约 12–15 ms/s，画面静止时也在跑。
- 未测：70 个逐房间 SVG 滤镜在相机每帧移动时的 GPU 光栅化开销；覆盖层被 `ShowWindow(SW_HIDE)` 隐藏后 WebView2 是否仍在执行 rAF。两项都需要 Windows/GPU 环境。

### 候选的处理（用户授权由实施方决定，2026-10-31）

- `backdrop.ts` 测量循环：立项为子任务 5。它在正式包中同样逐帧运行（开发版剖析约 12–15 ms/s，画面静止时也在跑），且只改一个模块。
- 高刷新率显示器上的雷达帧率：暂不立项。rAF 让雷达渲染次数随刷新率增长（144 Hz 约 159 次/秒），但子任务 1 之后 144 Hz 下最坏配置的模型计算只剩约 5 ms/s；
  剩余的是雷达子树的 React 渲染与 DOM 写入，本环境测不出它在 WebView2 高刷下的实际占比。限频要按刷新率整数分频并牺牲当初选 rAF 换来的旋转平滑，
  收益未证实前不值得。重新考虑的条件：Windows 高刷实测中雷达渲染是覆盖层主线程的主要开销。
